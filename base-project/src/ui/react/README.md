# template.ui

React front end for `template.api`. Vite + React 19 + TypeScript, styled with
Tailwind CSS v4, wired up with the TanStack suite.

## Running it

The UI needs the API for its data. Start both:

```bash
# terminal 1 — API on http://localhost:5058
cd ../../template.api
dotnet run --launch-profile http

# terminal 2 — UI on http://localhost:5173
npm install
npm run dev
```

Or run everything at once with `aspire run` from the repository root, which also
starts the Blazor front end against the same API.

Vite proxies `/api/*` to the API (see `vite.config.ts`), so the browser stays
same-origin and this app needs no CORS configuration of its own. Under the Aspire
AppHost the proxy target comes from `API_HTTP`; standalone it falls back to
`http://localhost:5058`. Point it elsewhere with the `VITE_API_TARGET`
environment variable.

| Script              | Does                                     |
| ------------------- | ---------------------------------------- |
| `npm run dev`       | Dev server with HMR                      |
| `npm run build`     | Typecheck, then production build to `dist` |
| `npm run typecheck` | Typecheck only                           |
| `npm run lint`      | oxlint                                   |
| `npm run preview`   | Serve the built `dist`                   |

## Layout

```
src/
  routes/           file-based routes — the file path IS the URL
    __root.tsx      layout, nav, devtools, router context type
    index.tsx       home; plain useQuery against the API
    counter.tsx     store-to-render check; no HTTP, no config, no services
    weather.tsx     forecast grid; useLiveQuery against the DB collection
  db/collections.ts TanStack DB collections
  store/            TanStack Store — client-only UI state
    preferences.ts  temperature unit + theme (writes <html data-theme>)
    counter.ts      the /counter count
  lib/api.ts        typed fetch wrappers for template.api
  lib/query-client.ts  the shared QueryClient
  components/ui/    the design system - one file per approved component
  components/styleguide/  chrome for the /styleguide page; not for product screens
  routeTree.gen.ts  generated by the router plugin — do not edit
```

## The four TanStack pieces

**Router** — routes are files under `src/routes`. Adding `src/routes/about.tsx`
that exports a `Route` created with `createFileRoute('/about')` creates `/about`;
the plugin regenerates `routeTree.gen.ts` on save. Links are typed, so a typo in
a `to=` prop is a compile error.

**Query** — one `QueryClient` in `src/lib/query-client.ts`, shared by hooks and
collections. `src/routes/index.tsx` shows the direct `useQuery` form.

**DB** — `weatherCollection` wraps the same query in a live collection.
Components read it with `useLiveQuery`, which re-runs incrementally on change
rather than re-filtering the whole array each render, and `getKey` lets rows
update in place across refetches.

**Store** — `preferencesStore` holds the °C/°F toggle. Use it for state the
server does not own; anything that comes from the API belongs in Query or DB.

## Design system

Every screen is built from the components in `src/components/ui/`, and every one
of those is built from the tokens in `src/index.css`. `/styleguide` renders the
whole set live - each component with its variants, its states, an accessibility
note and the code to copy. Read it before writing new markup; a variant that is
missing belongs there first, not in one screen.

The Blazor front end publishes the same sections in the same order at its own
`/styleguide`, mapped onto FluentUI. The two are meant to be read side by side.

### Tokens

Tailwind v4, configured in CSS - there is no `tailwind.config.js`. The tokens
live in `src/index.css` under `@theme`, which is what teaches Tailwind the
utility names:

| Group | Tokens |
| --- | --- |
| Surface + content | `surface`, `surface-raised`, `surface-sunken`, `border-subtle`, `border-strong`, `content`, `content-muted`, `content-disabled` |
| Brand | `brand`, `brand-subtle`, `brand-contrast` |
| Intents | `intent-{info,success,warning,danger}`, each with a `-subtle` background and a `-contrast` foreground |
| Focus | `focus-ring` - its own token, not the brand |
| Shape | `radius-control`, `radius-surface`, `radius-pill` |
| Elevation | `shadow-raised`, `shadow-overlay` |
| Motion | `--motion-fast`, `--motion-slow` |

Use the token utilities (`bg-surface`, `rounded-control`, `shadow-raised`) and
never a raw value like `bg-slate-800` or `rounded-lg`: a raw color has one value
and so breaks whichever theme it was not picked for, and a literal radius drifts
the moment one component is restyled.

Each color token carries **both** palettes in one definition through
`light-dark()`, resolved against the `color-scheme` set on `:root`. That is why
there is no second dark block to keep in sync, and why `@theme` hoisting to
`:root` no longer matters. `src/store/preferences.ts` writes `<html data-theme>`,
and the attribute selectors in `index.css` override the OS setting in both
directions.

Motion is the exception: Tailwind v4 has no duration namespace, so
`--motion-fast` / `--motion-slow` sit on `:root` and are read as
`duration-[var(--motion-fast)]`. They collapse to `1ms` under
`prefers-reduced-motion`, so no component opts in individually.

The same token names exist on the Blazor side, in
`src/ui/blazor/Template.Blazor.Maui.Pages/wwwroot/app.css`, aliased onto
FluentUI's own variables. **Adding a token here means adding it there.**

### Adding a component

1. One file in `src/components/ui/`, named after the component.
2. Tokens only - no raw colors, radii or shadows.
3. Type the props off the underlying element and spread `...props`, so the
   component never blocks an attribute a caller needs.
4. If it takes user input, read `useFieldControlProps()` from `field.tsx` so it
   picks up the surrounding `Field`'s id, `aria-invalid` and `aria-describedby`.
5. Add a section to `src/routes/styleguide.tsx` showing every variant and state,
   with an accessibility note - and add the matching section to the Blazor guide.

## Adding an endpoint

1. Add a typed fetch function to `src/lib/api.ts`.
2. For one-off reads, call it from a route with `useQuery`.
3. For data several components share or mutate, add a collection in
   `src/db/collections.ts` and read it with `useLiveQuery`.

## After adding a route

`src/routeTree.gen.ts` is written by the TanStack Router Vite plugin, so a
brand-new file under `src/routes/` will fail `npm run typecheck` — and therefore
`npm run build`, which typechecks first — until the plugin has run. Start
`npm run dev`, or run `npx vite build` once, then typecheck.

## Progressive web app

Configured by `vite-plugin-pwa` in `vite.config.ts`. Installable, with an offline
app shell; API responses are never cached, so offline `/weather` shows its error
state while `/counter` keeps working.

`registerType: 'autoUpdate'` plus `injectRegister: 'auto'` means the plugin
injects the registration script into `index.html` — **`src/main.tsx` contains no
service-worker code**, and shouldn't gain any.

The worker is live in dev too, but precaches nothing there: Vite serves unhashed
ES modules, so there is no precache manifest to build and it supplies only
`navigateFallback`. If it ever serves something stale, the fix is *Application →
Service Workers → Unregister*, then a hard reload.

To exercise the real offline shell you need a production build:

```bash
npm run build && npm run preview
# then DevTools -> Application -> Service Workers -> tick Offline, and reload
```

`navigateFallbackDenylist: [/^\/api\//]` is load-bearing. This app is same-origin
with the API — the Vite proxy in dev, YARP after `PublishAsStaticWebsite` — so
without it the worker would answer `/api/*` navigations with the app shell.

`public/icon-maskable.svg` is the favicon mark padded into the maskable safe zone.
It is placeholder branding. Note that iOS ignores SVG home-screen icons and falls
back to a page screenshot; a proper one means adding a PNG `apple-touch-icon`.
