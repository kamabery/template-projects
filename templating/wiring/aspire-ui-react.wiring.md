# Wiring: React front end

`dotnet new` can write files but cannot merge into an existing `apphost.cs`. These are the edits
that finish the job. Apply them exactly, then delete the `.scaffold/` directory.

Nothing goes into the solution file: `src/ui/react` is an npm workspace, not an MSBuild project.
The AppHost owns it through `AddViteApp`.

---

## 1. `.aspire/apphost.cs` — package directive

Insert **above** the line containing `<<addon-packages>>`:

```csharp wire file=.aspire/apphost.cs at=<<addon-packages>> pos=above
#:package Aspire.Hosting.JavaScript@13.5.1
```

## 2. `.aspire/apphost.cs` — the resource

Insert **below** the line containing `<<addon-resources>>`:

```csharp wire file=.aspire/apphost.cs at=<<addon-resources>> pos=below
// React, on the Vite dev server.
//   WithReference(api)  -> API_HTTP / API_HTTPS, read by vite.config.ts for the /api proxy.
//   WithOtlpExporter    -> OTLP endpoint + api key for browser RUM. HttpProtobuf is required:
//                          browsers cannot speak the gRPC protocol the .NET services use.
var ui = builder.AddViteApp("ui", "../src/ui/react")
    .WithNpm()
    .WithReference(api)
    .WaitFor(api)
    .WithOtlpExporter(OtlpProtocol.HttpProtobuf)
    .WithExternalHttpEndpoints();
```

## 3. `.aspire/apphost.cs` — publish behaviour

Insert **below** the line containing `<<addon-publish>>`:

```csharp wire file=.aspire/apphost.cs at=<<addon-publish>> pos=below
// On publish the React UI becomes a static site behind YARP, which also reverse-proxies /api to
// the API so the browser stays same-origin exactly as it does in dev.
#pragma warning disable ASPIREJAVASCRIPT001
ui.PublishAsStaticWebsite("/api", api);
#pragma warning restore ASPIREJAVASCRIPT001
```

---

## 4. `IaC/` — nothing to merge

`IaC/frontend.react.tf` was added by this add-on and Terraform loads every `*.tf` in that directory,
so it is already wired. Two things it does that are worth knowing:

- The Static Web App is **Standard**, not Free, because only Standard can link a backend. The link
  points at the API container app, which puts the API on the same origin as the SPA at `/api` -
  exactly what Vite's proxy does in development and what `PublishAsStaticWebsite("/api", api)` does
  on an Aspire publish. So the deployed React app needs **no** CORS entry either.
- A container app can be the linked backend of exactly one static web app. That limit never bites
  here, because a scaffold has one front end and this is it.


## Notes for the generated docs

- The React app reaches the API through Vite's `/api` proxy, so it is same-origin and needs **no**
  CORS entry on the API.
- `envPrefix: ['VITE_', 'OTEL_']` in `vite.config.ts` is what lets `src/lib/telemetry.ts` read the
  AppHost's `OTEL_*` values. Outside the AppHost no endpoint is set and browser RUM turns itself
  off - that is the intended standalone behaviour, not a bug.
- `npm run lint` runs oxlint, not ESLint. `noUnusedLocals` is on, so an unused import fails the
  build.
- `src/routeTree.gen.ts` is generated by the router plugin. Never edit it; if `tsc` fails on a new
  route, run `npx vite build` once so the plugin regenerates it, then typecheck.
- The design system is `src/components/ui/` - one file per approved component - built entirely from
  the tokens in `src/index.css`. `/styleguide` renders the whole set live, with every variant, every
  state, an accessibility note and the code to copy. Compose from those components rather than
  writing new markup, and never reach for a raw value: not `bg-slate-800`, and not `rounded-lg` or
  `shadow-sm` either.
- Each color token carries both palettes in one definition through `light-dark()`, so there is no
  second dark block. Motion is the exception - Tailwind v4 has no duration namespace, so
  `--motion-fast` / `--motion-slow` sit on `:root` and are read as `duration-[var(--motion-fast)]`.
- If this scaffold also has the Blazor front end, it declares the same token names in
  `Template.Blazor.Maui.Pages/wwwroot/app.css` as aliases onto FluentUI's variables, and publishes
  the same style guide sections in the same order at its own `/styleguide`. Nothing enforces that
  the two agree: adding a token or a component to one means adding it to the other.
